# 麦麦省钱最优解引擎 · mcd-saver

> 同一份订单，点法不同，价差能到 37%。
> 基于麦当劳中国官方 MCP，实时拉菜单、拆套餐、核券、算价，给你最低实付的那一版购买方案 —— 顺带告诉你这顿多少大卡、脂肪占比多少，以及低脂/低糖/高蛋白该怎么选。

[![Node](https://img.shields.io/badge/node-%3E%3D18-brightgreen)](https://nodejs.org/)
[![MCP](https://img.shields.io/badge/MCP-mcd--mcp-blue)](https://github.com/M-China/mcd-mcp-server)

## 它解决什么

麦当劳的菜单里藏着四层信息差，肉眼很难算清：

1. **套餐 vs 单点** —— 「巨无霸 + 薯条 + 可乐」单点 ¥50，而「巨无霸三件套」只要 ¥37，省 26%。
2. **"随单购价"陷阱** —— 菜单上「巨无霸四件套」标 ¥32，但那是**随单购麦金卡优惠价**；不买卡的实际核价是 ¥59.50，持麦金卡随单购也要 ¥41.90。标价比三件套便宜 5 块，真付却贵 22.5 块。
3. **套餐溢出** —— 有的四件套比三件套还便宜，还白送一份麦乐鸡，但你不算就不知道。
4. **积分该换哪张券** —— 积分商城一次返回 24 件商品，**其中 15 件已经过期**（官方列表不自动清理），而每张券值不值，取决于它换来的东西单点要多少钱。

`mcd-saver` 把前三层交给官方 `calculate-price` 接口**逐方案真实核价**，不靠猜、不靠规则硬算；第四层用官方时间接口过滤过期商品，再按「每 100 积分省多少」排序。

## 快速开始

### 1. 申请 MCP Token

登录 [麦当劳 MCP](https://mcp.mcd.cn) → 右上角「控制台」→「激活」→ 复制 Token。

### 2. 配置

```bash
git clone https://github.com/zddamn/mcd-saver.git
cd mcd-saver
cp ENV.example .env      # 填入你的 Token
export MCD_MCP_TOKEN=你的Token
```

### 3. 跑

```bash
# 求最低实付方案
node src/cli.js best --want "巨无霸,薯条,可乐"

# 换个门店（按位置搜索）
node src/cli.js best --want "板烧鸡腿堡,薯条" --city 厦门 --kw 软件园

# 看套餐省钱榜（套餐现价 vs 成分单点价）
node src/cli.js menu

# 盘点券：本店可用 / 卡包 / 可领
node src/cli.js coupons
node src/cli.js coupons --bind      # 一键领取所有可领券

# 生成可视化 HTML 报告
node src/cli.js report --want "巨无霸,薯条,可乐" --html report.html

# 积分商城：940 分该换哪张券（自动过滤已过期商品）
node src/cli.js points
```

### 积分：换哪张券最值

```bash
node src/cli.js points           # 积分余额 + 可兑换券性价比榜
node src/cli.js points --all     # 连已过期的也列出来（看看错过了什么）
```

`best` 命令会自动带上积分建议 —— 如果换券比现金方案更省，直接告诉你省多少：

```
积分换券方案（比上面的最优解更省）
  · 花 500 积分换「板烧可乐组合」券（¥17.90）
    抵掉：可乐、板烧鸡腿堡
    合计 ¥17.90，比最优现金方案省 ¥15.10
```

**为什么需要这一层**：官方 `mall-points-products` 一次返回 24 件商品，其中 15 件的 `downTime` 早于今天 —— 列表不会自己清理。本项目用官方 `now-time-info` 拿服务器时间过滤，只对还能换的券排序，排序口径是**每 100 积分能省多少钱**（券内商品单点价 − 券价）。

券面写「任选 / 指定」、或本店菜单没有对应单品的（如「指定小食任选」「圆筒冰淇淋」），**不硬猜价格**，单独列为「不自动估价」，避免给出错误数字。

### 饮食偏好：低脂 / 低糖 / 低钠 / 高蛋白 / 低卡

```bash
# 按偏好推荐餐品（主食 / 小食 / 甜品 / 饮料 分组各推 top5）
node src/cli.js diet --diet low-fat
node src/cli.js diet --diet high-protein
node src/cli.js diet --diet low-sugar      # 官方无糖字段，以碳水近似
node src/cli.js diet --diet low-sodium
node src/cli.js diet --diet low-calorie

# 省钱的同时兼顾偏好：在同样省钱的方案里挑最符合的
node src/cli.js best --want "巨无霸,薯条,可乐" --diet low-fat

# 热量上限：超标的方案直接过滤掉
node src/cli.js best --want "巨无霸,薯条,可乐" --max-kcal 800
```

排序指标不用绝对值（绝对值对"一份沙拉 vs 一个汉堡"不公平），而是用**供能比 / 密度**这类营养学通用口径：

| 偏好 | 排序指标 |
|---|---|
| 低卡 `low-calorie` | 总热量 kcal |
| 低脂 `low-fat` | 脂肪供能比（脂肪 g × 9 ÷ kcal） |
| 低糖 `low-sugar` | 碳水供能比（碳水 g × 4 ÷ kcal） |
| 低钠 `low-sodium` | 钠密度（钠 mg ÷ kcal） |
| 高蛋白 `high-protein` | 蛋白供能比（蛋白 g × 4 ÷ kcal） |

`best --diet` 的逻辑是：**省钱是主目标，健康是在省到位的方案里挑**。默认只为偏好多让路 `max(3元, 最低价15%)`，可用 `--tolerance` 调整。

零第三方依赖，Node 18+ 直接跑（用的是内置 `fetch`）。

## 工作原理

```
用户输入 "巨无霸,薯条,可乐"
        │
        ▼
┌───────────────────────────────────────────────┐
│ 1. query-nearby-stores     定位门店 storeCode    │
│ 2. query-meals             拉取全量菜单（94 项）│
│ 3. query-meal-detail       拆开 39 个套餐的成分 │
│ 4. query-store-coupons     拉本店可用券         │
│ 5. available-coupons       拉可领未领的券       │
│ 6. list-nutrition-foods    拉官方营养数据（160）│
└───────────────────────────────────────────────┘
        │
        ▼
  名称归一化对齐（"可乐中杯" → "可乐"）
        │
        ▼
  DFS 枚举套餐/单品组合（允许套餐溢出 ≤2 件）
        │
        ▼
  按菜单理论价升序，取前 N 个
        │
        ▼
┌───────────────────────────────────────────────┐
│ 6. calculate-price   官方逐方案真实核价（含券）│
└───────────────────────────────────────────────┘
        │
        ▼
  按实付升序输出 + 加价升级建议 + HTML 报告
```

### 四个关键设计

**① 名称归一化对齐**
套餐子项的编码和菜单单品编码不是同一套（套餐里可乐是 `3050`，菜单里是 `9900008751`）。直接比编码永远匹配不上，所以引擎把商品名归一化（去「中杯/大杯/中/大/小」、去「【美汁源】」、去「4块」这类数量词），在**名称维度**做覆盖判定，下单时再用真实编码。

**② 允许套餐溢出**
严格"套餐成分 ⊆ 需求"会漏掉真实世界里更便宜的大套餐。引擎允许溢出 ≤2 件，把选择权交给官方核价结果，并明确标出 `[+白得的东西]`。

**③ 价格一律官方核价**
所有展示的金额都来自 `calculate-price` 返回，引擎自己不做任何优惠计算 —— 所以「随单购价」这类陷阱会被自动暴露。连"加价升级"建议也只认核价：菜单标 ¥32 的四件套，核价是 ¥59.5，引擎不会建议你去"升级"。

**④ 套餐热量靠成分累加，而不是查表**
官方营养表只有 160 条单品记录，没有套餐。引擎把套餐拆成成分后逐个查表再求和 —— 「巨无霸三件套」= 巨无霸 513 + 中薯条 289 + 可乐中杯 147 = **949 kcal**。
成分名和营养表名还有噪声差异（`原味双层深海鳕鱼堡` vs `双层深海鳕鱼堡`、`麦辣鸡翅4块` vs `麦辣鸡翅-2块`），所以用「精确 → 归一化 → 包含回退」三级匹配。
匹配不上的（新品如龙焰系列）会标 `*`，且默认不进推荐榜 —— 宁可少推荐，也不能给偏低的假数据。

## 用到的麦当劳 MCP 工具

| 工具 | 用途 |
|---|---|
| `query-nearby-stores` | 按位置/收藏定位门店，取 storeCode |
| `query-meals` | 拉全量菜单与现价/原价/优惠类型 |
| `query-meal-detail` | 拆套餐成分（rounds → choices） |
| `query-store-coupons` | 本店可用券（唯一带 couponId/couponCode 的来源） |
| `query-my-coupons` | 卡包资产盘点与到期提醒 |
| `available-coupons` / `auto-bind-coupons` | 可领券查询与一键领取 |
| `calculate-price` | **官方核价**，本项目的价格真相来源 |
| `list-nutrition-foods` | 官方营养数据（热量/蛋白/脂肪/碳水/钠/钙），支撑热量标注与饮食偏好排序 |
| `query-my-account` | 积分账户余额（可用 / 已用 / 已过期），判断哪张券换得起 |
| `mall-points-products` | 积分商城商品券（积分门槛、券价、有效期） |
| `now-time-info` | **服务器时间** —— 积分商城不清理过期商品，必须靠它过滤 |

完整调用链路与业务价值见 [MCP_INTEGRATION.md](./MCP_INTEGRATION.md)。

## 调用约束（官方限制与应对）

官方规定**每个 Token 每分钟最多 600 次请求**，超限返回 429。引擎的应对：

| 机制 | 实现 |
|---|---|
| 客户端限流 | 滑动窗口 480 次/分钟（留 20% 余量），超限自动等待 |
| 429 退避重试 | 1s → 2s → 4s，最多 3 次 |
| 401 明确提示 | 直接告诉你 Token 失效并给申请入口 |
| 控量 | 套餐成分缓存 6 小时；随单购双价只对前 5 个方案核 |

单次求解约 45~55 次请求（首次），命中缓存约 10 次 —— 离上限很远，但连续批量运行时限流器会自动兜底。

## 目录结构

```
src/
  mcp-client.js   MCP Streamable HTTP 客户端（零依赖，内置 fetch）
  menu.js         菜单加载 / 套餐成分展开 / 名称归一化 / 营养挂载
  nutrition.js    官方营养数据解析、三级匹配、供能比计算、饮食偏好定义
  coupons.js      券资产加载与匹配
  points.js       积分账户 / 积分商城 / 券面解析 / 性价比估算（含过期过滤）
  solver.js       方案枚举（DFS）+ 官方核价 + 饮食偏好筛选 + 加价升级分析
  reporter.js     终端表格输出 / 饮食推荐榜 / 积分榜 / HTML 报告生成
  cli.js          命令行入口
  cache.js        菜单本地缓存（6 小时，避免重复打 MCP）
SKILL.md          WorkBuddy Skill 定义（可直接被 AI 调用）
```
